### Breaking

- `LeiosLedgerView` gained `llvMaxEbTxsSize`, the total size an endorser block's transactions may amount to, forecast via the ledger's `maxEndorserBlockTxsSizeForecastL`. `ResolveLeiosBlock` gained `getLeiosMaxEbTxsSizeFromView` to read it, defaulting to 0 for an era without the parameter --- which is the truth rather than a placeholder, since such an era has no endorser blocks and one offered anyway may reference nothing.

- `leiosFetchLogicIteration` takes a `SlotNo -> Either OutsideForecastRange BytesSize`, the bound forecast from the immutable tip to a slot. `assignBody` consults it for the offered point's slot, so one `EbHash` announced in two slots is requested under each slot's own bound. The bound is a protocol parameter --- a function of the slot and nothing else --- so there is nothing per endorser block to retain and nothing to keep coherent.

- `PeerOffer` gained `poMaxEbTxsSize`, `SJust` only for an offer synthesised from a CertRB roll-forward. That header was validated against the view at its predecessor's slot, which is the announced endorser block's own slot, and `CsClient.leiosMsgRollForwardCallback` now receives that view (so `recordCertRbOffer` and `checkMsgRollForwardForLeiosOffers` take it). Retaining it there is what keeps the Recovery Path alive on a sparse chain: the ChainSync client can validate a header our immutable tip cannot forecast to, and a CertRB cannot be selected until we hold its endorser block, so a fetch blocked on a failed forecast would keep the immutable tip from advancing and the forecast from ever succeeding. A LeiosNotify offer needs no such retention --- the announcement backing it was accepted by forecasting from the immutable tip to that same slot.

- `LeiosBlockRequest` is a record: `lbrPoint`, `lbrOfferedSize` and the new `lbrMaxEbTxsSize`, which names the two sizes rather than leaving them adjacent positional `BytesSize`es. Only the point goes to the peer; both sizes are what the response is validated against, so `processLeiosBlock` reads the bound off its `LeiosBlockSource` rather than looking anything up, and the check sits outside the `LeiosOutstanding` lock: it is decided by the body and the request alone.

- `ExnLeiosBlockWrongSize` is now a constructor of `ExnLeiosWellHashedBodyRejected`, alongside the new `ExnLeiosClosureTooBig`. Both are thrown by `processLeiosBlock` for a body that hashes to the endorser block we asked for and is still unacceptable, and both only once the lock is released, since throwing under it would roll back the record they rely on.

- `LeiosTestView` gained `ltvMaxEbTxsSize`, fixed for a whole test run by `ltlcMaxEbTxsSize` and defaulting to `maxBound`, so a test that does not care about the bound never trips it.

### Non-Breaking

- An arriving endorser block's references are weighed against the bound before any closure job is built, and the peer that served it is disconnected. Bounding the encoded body does not bound its closure: a reference is charged the CBOR digits of the size it claims, so a body within `maxLeiosEbBytesSize` (512 KiB) could name hundreds of megabytes of transactions, against a protocol intent of twelve. The per-job caps `mkLeiosJobPool` takes partition that work, they do not cap it.

- A rejected endorser block is recorded as acquired with an empty job pool and never written to the LeiosDb, so its closure is never fetched, it is never offered on, and the next peer to serve the same bytes does not cost us the work again. No honest peer sends one: such an endorser block can never be certified, because an honest committee member applies the same bound, so an honest peer that fetched it rejected it too and never stored or offered it.
