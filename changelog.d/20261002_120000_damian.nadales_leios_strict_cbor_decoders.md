### Breaking

- `TxHash` and `EbHash` now hold a `PackedBytes 32` in place of a
  `ByteString`. `ebHashBytes` is no longer a record field. Use
  `txHashBytes` and `ebHashBytes` to get the bytes, and the new
  `txHashFromBytes` and `ebHashFromBytes` to build a hash. Both fail unless
  the input is 32 bytes.

- The `TxHash`, `EbHash` and `RbHash` decoders reject any length other than
  32 bytes. This includes the EB hash in the `EbAnnouncement` of a Praos
  header and the RB hash in a Leios vote. Older nodes accept these hashes at
  any length.

- `codecLeiosFetch` and `decodeLeiosFetch` take the largest EB tx count as a
  new first argument. The decoders reject an `MsgLeiosBlockTxs` tx count above
  it, or one that differs from the number of txs that its bitmaps request.
  `decodeBitmaps` stops after the entries that cover that many txs. It also
  rejects a zero bitmap, an index at or above that entry limit, and indices
  that are not strictly ascending. The LeiosFetch server no longer checks
  these cases with `error`.

- `decodeLeiosEb` rejects an item count that is not between 1 and
  `maxTxsPerEb`.

### Patch

- The LeiosDb reads throw a `LeiosDbException` if the database holds a tx
  hash or an EB hash that is not 32 bytes. The LeiosFetch server throws one if
  the database holds more rows for an EB than `maxTxsPerEb`. A database that
  an older build wrote can hold such data.
